- When rm -rf, make sure you are 100% sure about everything this is going to irrecoverably wipe; consider mv x x~ instead
- Use uv for everything Python-related (venv creation, package installs, running scripts)
- Any subagents use for research should use the `research` mode (mechanical low-creativity work requiring advanced reasoning should use the `deep` mode).
- Research subagent output that goes *beyond* pure research (gradings, verdicts, decisions) must get an explicit review of its final decisions — by you or a smart/deep-mode reviewer subagent. Pure research needs no review pass. Ideal pipeline: research subagents for research → deep/smart subagents for grading → you critically eyeball key sources + main conclusions yourself.
- Reviewers come from a different lab than the author: GPT-authored work (`research`/`deep`) → `smart` (Claude) reviewer; Claude-authored → `deep` (GPT). Both are flat-rate subscriptions. `oracle` (Gemini) is pay-per-token — use it only as a third opinion when GPT and Claude reviews disagree on a decision pasky has to sign.
- Side agents (children): never message the parent — not progress, not status, not questions. Put results/summary in your artifact; if blocked, write the question in your own pane. Either way go idle; the parent polls (agent-check shows `waiting_user` + your last output).
- When `git rebase` etc., make sure to GIT_EDITOR=true to avoid hangs
- Never mask out issues by using patterns like `kill 3273547 2>/dev/null; echo "killed"`
- After completing a change (code/docs), commit it with a clear message once it builds/tests green — don't leave the work uncommitted waiting to be asked.
- Entries under `packages/` are git SUBMODULES, each its own repo. To change a file inside one, commit INSIDE that submodule first, then bump the outer repo's pointer with a scoped `git add packages/<name>`. Never `git add -A` from the outer repo for submodule work (it won't reach into submodules and will sweep up unrelated dirty files).
- Anytime you are going to call `find`, stop and think - 80% likelihood that you are taking a stupid approach (instead of loading an object from storage properly, using `git grep`, etc.), all finds take very long and are I/O heavy.
- When researching/recommending products to buy (yourself or via subagents): ONLY precise product links (exact product page, verified by visiting it — name, price, stock). Never generic category links, never linkless claims.
- Releasing a JS package means BOTH halves: `npm publish` AND a GitHub release (`gh release create`) with a proper changelog summarizing the commits since the last tag. The GH release is the half we often forget.
- If you're addressed as "Bob" it means you are going down a wrong path and pasky is frustrated.
- Review/subagent scripts must be memory-bounded on dense meshes, images, and large arrays. A Viktor-mask review once exhausted roughly 55 GB by running an unconstrained Python geometry check. Before execution, inspect dimensions and algorithmic allocation, avoid full ray/triangle or other Cartesian-product arrays, batch/stream work, and impose a practical process memory limit; do not blindly rerun a failed command.
- Type non-ASCII (—, ≥, “”) literally in edit args, never as `\uXXXX`; on edit failure, retry edit, don't switch to Python.
- Before adding a test (including one a reviewer suggests), check that existing tests don't already cover the behavior, and don't write tests that only restate config/data values.
- Periodic/background jobs (cron, systemd timers, ~/projects/watchers) get API keys, `pi` and nvm node by sourcing `~/.bashrc` (`. $HOME/.bashrc;` / `bash -c '. "$$HOME/.bashrc"; exec ...'` in units) — never copy keys into separate env files.
- For LLM judgement in scripts/jobs, prefer pi's `research` mode (`pi -p --model <modes.json research>`) over the local llama-server Qwen; use local Qwen at most as a side-by-side calibration arm. (*Inside* your session, of course use the subagents or side agents tool rather than spawning your own pi.)
